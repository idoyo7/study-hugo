# 문제 정의와 결정 2축

{{< callout type="info" >}}
- 목적은 과거 장애 재조사용 메트릭 400일 보관. `>90d` 구간은 5m 해상도 허용(확정), 전 메트릭 커버리지 필요, OSS 우선.
- 결정은 2축: (1) 무엇을 보관하나(raw 400d 전부 vs raw 90d + 5m 집계 400d — 후자가 비용을 자릿수로 낮춥니다) · (2) 어디에 저장하나(VM은 S3를 primary로 지원하지 않아 EBS 위에 둡니다).
- 서울 리전 단가는 sc1 < S3 Standard < st1 < gp3 — "S3라서 싸다"는 성립하지 않습니다.
- 확정 시나리오(raw 90d + 5m 집계 400d) 기준 VM 아카이브안이 월 $385~416로 최저, 단순 확장($1,642)보다 자릿수로 쌉니다.
{{< /callout >}}

메트릭 400일 보관 문제를 정의하고 비용을 자릿수 단위로 좌우하는 두 결정축(무엇을 보관 / 어디에 저장)을 정리합니다. 시나리오별 저장량·비용 규모와 검증된 서울 리전 단가 요약표를 함께 싣습니다.

관련 문서: [00 인덱스]({{< relref "_index.md" >}}), [02 VM 아카이브(권장)]({{< relref "02-vm-archive.md" >}}), [06 스토리지 단가]({{< relref "06-storage-pricing.md" >}}), [07 핵심논점]({{< relref "07-streamaggr-vs-downsampling.md" >}})

## 1. 문제 정의

대상: chain 클러스터 VMCluster OSS (vmstorage×4, 900Gi gp3, RF=2, 현행 80d) / AWS ap-northeast-2(서울).

확정된 요구는 넷입니다.

- 목적 = 과거 장애 재조사. 지난 장애를 되짚어 원인과 추세를 다시 확인하려고 400d를 보관합니다.
- **>90d 구간은 5m 해상도 허용(확정).** 90일을 넘긴 데이터에 raw 30s는 불필요하고 5m이면 충분하다고 사용자가 확정했습니다.
- 전 메트릭 커버리지. 재조사 시점에 어떤 메트릭이 필요할지 미리 알 수 없으므로 keep-list를 두지 않고 전 메트릭을 대상으로 합니다.
- OSS 우선. VM Enterprise는 비교 기준으로만 다루고 기본 배제합니다.

400d 보관 비용의 자릿수를 먼저 정하는 것은 엔진 선택이 아니라 데이터 형태 선택입니다. 그래서 이 문제는 서로 독립인 두 결정축으로 나뉩니다.

## 2. 결정은 2축

### 축 1 — 무엇을 400d 보관하나 (비용을 자릿수로 가름)

| 보관 형태 | 저장량(현 워크로드 외삽) | 월 저장비 규모 |
|---|---|---|
| **① raw 30s × 400d 전 구간** | ~18.0 TiB | **~$1,642/mo** |
| **② raw 90d + 5m 집계 400d** | hot ~4.0 TiB + 아카이브 0.9~2.7 TiB | **~$385~416/mo** |

①은 현 구조(RF2 gp3)를 그대로 연장한 것이고 ②는 아카이브를 RF1 저가 EBS에 둡니다. ②의 저장비는 넓게 잡으면 $390~510까지 갑니다.

"5m 허용"이 확정됐으므로 ②가 기본 전제입니다. 그러면 남는 질문은 하나입니다.

VM OSS에는 다운샘플링이 없습니다. `-downsampling.period`는 Enterprise 전용(contact-sales)입니다. 이 갭을 무엇으로 5m을 만들어 메우는가?

후보는 셋입니다.

- vmagent streamAggr(OSS, v1.87.0+) — 인제스트 시점에 5m 집계를 만들어 별도 장기 tier로 보냅니다(사전 집계) → VM 아카이브안. 개념 상세는 [수집 (vmagent·vminsert)]({{< relref "../victoriametrics/concepts/03-ingestion.md" >}}).
- Thanos compactor downsampling — raw 블록을 S3에 쌓아두고 사후에 5m/1h 블록을 만듭니다(사후 집계) → Thanos안.
- Mimir — 다운샘플링이 OSS/GEM 어디에도 없습니다(3.0에서도 미추가) → 이 요구에서는 사실상 탈락.

사전 집계 vs 사후 집계의 대비가 이 챕터의 주된 논점입니다. 판정과 비교표는 [07 핵심논점]({{< relref "07-streamaggr-vs-downsampling.md" >}})에서 다룹니다.

### 축 2 — 어디에 저장하나

- VM은 S3를 primary(쿼리 가능) 스토리지로 지원하지 않습니다. 2019년 issue #38 이래 2026-07 현재까지 나오지 않았습니다. 유지보수자의 "VictoriaLogs 구현 후 검토" 입장과 #38 self-assign(2026-03)은 신호일 뿐 일정 약속이 없습니다 — 계획에 반영 금지. 따라서 VM 계열 아카이브는 EBS(gp3/st1/sc1) 위에, Thanos/Mimir 아카이브는 S3 위에 둡니다.
- 서울 단가 순서: `sc1 $0.0174 < S3 Standard $0.025 < st1 $0.051 < gp3 $0.0912` ($/GB·월).
- sc1이 S3 Standard보다 싸므로 "S3라서 무조건 싸다"는 서울 단가에서 성립하지 않습니다. 차이는 단가보다 내구성 모델(EBS 단일 볼륨 vs S3 11-nines)과 운영 컴포넌트 수에서 납니다. 압축·retention·볼륨 특성은 [저장과 압축]({{< relref "../victoriametrics/concepts/04-storage-and-compression.md" >}})와 [06 스토리지 단가]({{< relref "06-storage-pricing.md" >}})를 참조하세요.

## 3. 검증된 서울 단가 요약

> 출처: AWS Price List Bulk API (publicationDate 2026-07-10, AmazonEC2/S3 ap-northeast-2) — 적대적 검증 통과.

| 스토리지 | $/GB·월 | 성능/제약 | 부대 비용 |
|---|---|---|---|
| **EBS gp3** | **0.0912** | 3,000 IOPS·125 MiB/s 기본 포함, 1 GiB~64 TiB | 추가 IOPS/스루풋 별도 |
| **EBS st1** | **0.051** | 기본 40 MiB/s/TiB, 버스트 250 MiB/s/TiB, 125 GiB~16 TiB | — |
| **EBS sc1** | **0.0174** | 기본 12 MiB/s/TiB, 버스트 80 MiB/s/TiB, **최대 250 IOPS** | — |
| **S3 Standard** | **0.025** (≤50TB) | 11-nines 내구성 | GET $0.0035/1만건, PUT $0.0045/1천건 |
| **S3 Standard-IA** | **0.0138** | 최소 30일·128KB 과금 | **리트리벌 $0.01/GB** |
| **S3 Glacier IR** | **0.005** | 최소 90일·128KB 과금 | **리트리벌 $0.03/GB** |

같은 리전 S3↔EC2 전송은 무료입니다. IA/GIR은 GB당 리트리벌 수수료 때문에 자주 읽는 primary 저장에는 부적합합니다. 백업 콜드 사본에만 씁니다. 볼륨 타입 선택 가이드(gp3 시작 → IO 실측 후 st1/sc1)는 [06 스토리지 단가]({{< relref "06-storage-pricing.md" >}})의 주인 항목입니다.

## 4. 시나리오별 저장량·비용 규모

실측 대입용 공통 기호는 아래와 같습니다. 모든 수치는 프로비저닝 3,600 GiB를 100% 사용한다는 상한 가정입니다. 실사용률로 선형 보정합니다.

```
U(80d, RF2 상한) = 3,600 GiB
δ = U/(80×2)     = 22.5 GiB/day (사본 1개 기준)
S ≈ 2.2×10¹⁰ samples/day (~254k samples/s)
bytes/sample: VM ~1 B / Prom·Thanos 1.5~2 B / Mimir ~2 B (베스트케이스 0.4~0.8 B는 예산 근거 금지)

hot 90d RF2 gp3 = 4,050 GiB × 0.0912 = $369/mo
아카이브(VM 아카이브안) = δ × 400 × f × 단가  (f = 집계 축소율 0.1~0.3, 드라이런 실측 필요)
```

### 시나리오 ① — 400d 전부 raw 30s

| 옵션 | 저장 구성 | 월 저장비 |
|---|---|---|
| **단순 확장** — 현 클러스터 확장 | 18.0 TiB gp3 RF2 | **$1,642** (헤드룸 미포함 하한) |
| **VM raw 아카이브** — hot + VM raw 아카이브 | 9.0 TiB RF1 (sc1/st1) | **$485(sc1) / $787(st1)** |
| **Thanos** — hot + Thanos raw 400d S3 | 12.3~16.4 TiB S3 + Receive 로컬 EBS | **~$680~800 + 컴퓨트** |
| **Mimir** — hot + Mimir raw 400d S3 | ~16.4 TiB S3 | **~$740 + Kafka·컴퓨트** |

### 시나리오 ② — raw 90d + 전 메트릭 5m 집계 400d (사용자 확정 시나리오)

| 옵션 | 저장 구성 | 월 저장비 | 5m 구현 방식 |
|---|---|---|---|
| **VM아카이브 ★권장** | hot 90d $369 + 집계 0.9~2.7 TiB | **$385~416** | streamAggr(인제스트, OSS) |
| **Thanos** | hot 90d $369 + S3 14.9~30.7 TiB | **$780~1,200 + 컴퓨트** | compactor downsampling(사후) |
| **Mimir** | 5m 불가 → raw 400d 강제 | **부적합** | 다운샘플링 부재 |
| **확장+Ent** | `-downsampling.period=90d:5m` 한 줄 | **~$497 + 라이선스(비공개)** | Enterprise 다운샘플링 |

VM아카이브안의 월 저장비는 EBS 볼륨 타입에 따라 sc1 $385~416, st1 $415~507, gp3 $451~615로 늘어납니다.

시나리오 ②의 옵션 종합 비교표·판단 트리는 [07 핵심논점]({{< relref "07-streamaggr-vs-downsampling.md" >}})이 주인입니다. 권장 VM 아카이브안의 구성·가역성 상세는 [02 VM 아카이브]({{< relref "02-vm-archive.md" >}})에서 다룹니다.

불확실성 명시: (i) 모든 수치는 3.6 TiB 100% 사용 상한 가정 — 실사용률로 선형 보정합니다. (ii) VM 아카이브안의 f=0.1~0.3 범위는 드라이런 2주 실측이 확정치입니다(검증 필요). (iii) Thanos안의 S3 범위 하한/상한은 "5m·1h 블록이 raw와 비슷한 크기"라는 공식 문서 서술의 해석 범위입니다.
