## 전체 네트워크에서 AZ 간 내부 통신이 차지하는 비중

전체 네트워크 트래픽을 확인해 보니 **약 90%가 AZ 간 내부 통신(inter-AZ traffic)**이었습니다. 내부 컴포넌트끼리 주고받는 데이터가 AZ 경계를 넘는 양이 커서, 수집·전송 경로를 살펴봤습니다.

그중 vmagent가 다른 AZ의 타깃에서 scrape 응답을 가져오는 경로를 AZ별 수집으로 바꿨습니다. 이 변경으로 **전체 네트워크의 inter-AZ 트래픽을 약 10% 줄일 수 있었습니다.** 감소율의 기준은 변경 전 전체 inter-AZ 트래픽입니다.

아래에서는 이 효과를 만든 수집 구조와 분할 방식을 설명합니다. 환경명은 생략하고, 수치는 대략적인 규모로 표시했습니다. scrape 구간에서 줄일 수 있는 AZ 간 전송량은 하루 약 2TB로 추정했습니다.

## 분할 전 구성: 수집 응답이 하루 약 2TB씩 AZ를 넘는다

워크로드 수집 vmagent가 한 AZ에 한 대 있고, 다른 AZ 타깃에서 나오는 scrape 응답이 전체 전송량의 절반 정도인 구성입니다. 이 응답은 매번 AZ 경계를 넘어 agent로 들어옵니다. **타깃 → vmagent 구간에서만 하루 약 2TB가 AZ를 넘는 규모였습니다.**

수집한 메트릭은 원격 저장 클러스터에 보관합니다. 쓰기 경로는 **vmagent → 쓰기 LB → ingress → vminsert → vmstorage**입니다. vmagent는 샘플을 모아 압축해 보내고, vmstorage가 영속 데이터와 보관 용량을 관리합니다.

문제는 원격 저장소로 보내기 전의 **타깃 → vmagent** 구간입니다. 타깃이 어느 AZ에 있든 한 agent가 수집하기 때문에, 다른 AZ의 응답이 모두 AZ 간 전송으로 잡힙니다. scrape 응답의 대부분을 차지하는 Istio 사이드카 메트릭은 압축 없이 나가고, agent를 지난 뒤부터는 압축해서 보내므로 수집 구간의 전송량이 특히 큽니다.

전송 규모는 평균 scrape 전송량과 다른 AZ에서 발생하는 바이트 비중으로 추정했습니다. 파드 수가 비슷해도 응답 크기는 다를 수 있으므로, 타깃 개수보다 실제 전송량을 기준으로 봤습니다.

### 수집 구간부터 나눈 이유

scrape 응답에는 메트릭 이름과 라벨 문자열이 반복해서 들어갑니다. 특히 사이드카처럼 히스토그램과 라벨이 많은 타깃은 샘플 수에 비해 응답이 큽니다. 이 응답을 다른 AZ에서 가져온 뒤 압축해 저장소로 보내면, 가장 큰 데이터를 다루는 구간에서 이미 AZ 경계를 넘은 셈입니다.

그래서 먼저 수집 위치를 바꿨습니다. 저장소를 나누거나 보관 기간을 줄이지 않고도 적용할 수 있고, 수집 대상과 주기를 유지한 채 전송 경로만 비교할 수 있기 때문입니다. agent 한 대에 몰리던 수집 부하도 나눌 수 있지만, 이번 글에서 보는 효과는 AZ 간 전송량의 감소입니다.

## AZ별 분할: 같은 AZ에서 수집하고 원격 저장은 유지한다

vmagent를 한 대 추가해 **AZ a/c에 한 대씩, 총 두 대**로 나눴습니다. 아래에서는 기존 agent가 AZ c에 있고, AZ a에 agent를 추가하는 구성으로 설명합니다. 각 agent는 같은 AZ의 타깃을 수집한 뒤, 샘플을 모아 기존 원격 저장 엔드포인트로 보냅니다.

변경 후에도 타깃에서 나오는 응답량은 같습니다. **하루 약 2TB가 AZ를 넘어 이동하던 경로를 같은 AZ 안에서 끝내는 것**이 개선의 핵심입니다.

### 수집 대상과 실행 위치를 함께 나눈다

타깃의 AZ는 Node 라벨에서 읽습니다. `promscrape.kubernetes.attachNodeMetadataAll: "true"`로 Pod·Endpoint에 Node 메타데이터를 붙이고, `__meta_kubernetes_node_label_topology_kubernetes_io_zone`을 기준으로 수집 대상을 나눕니다. agent의 실행 AZ는 `nodeAffinity`로 고정합니다.

**수집 필터와 agent의 배치를 함께 맞춰야 합니다.** AZ a 타깃만 고르더라도 agent가 AZ c에 뜨면 응답은 여전히 AZ를 넘습니다. 반대로 agent만 두 AZ에 배치하고 수집 대상을 나누지 않으면 두 agent가 같은 타깃을 중복 수집할 수 있습니다.

| 구성 | 기존 agent · AZ c | 새 agent · AZ a |
|---|---|---|
| 수집 규칙 | AZ a 타깃 `drop` | AZ a 타깃만 `keep` |
| zone을 판정할 수 없는 타깃 | fallback으로 수집 | 제외 |
| VMStaticScrape·VMProbe·VMScrapeConfig | 전담 | 제외 |

### fallback은 기존 agent에 남긴다

기존 agent는 AZ c만 `keep`하도록 제한하지 않습니다. 양쪽을 각각 자기 AZ만 수집하도록 좁히면, zone 정보가 없는 타깃은 어느 쪽에도 들어가지 못합니다. 새 agent가 맡는 AZ a만 기존 agent에서 제외하면 신규 AZ나 zone 정보가 없는 타깃도 기존 agent에 남겨 수집 누락을 막을 수 있습니다. Node 메타데이터가 없거나 SD 구성이 다른 세 종류의 수집 설정도 기존 agent가 맡습니다.

이 fallback은 **분류되지 않은 타깃의 수집 담당을 정하는 규칙**입니다. 새 agent가 죽었을 때 기존 agent가 AZ a까지 대신 수집하는 장애 전환 기능은 없습니다. 분할 뒤에는 각 agent가 맡는 범위의 수집 중단을 따로 감시하고, 해당 AZ에 agent가 다시 뜰 노드 여유도 확보해야 합니다.

## 변경 전후: 하루 약 2TB의 AZ 간 scrape 전송을 줄인다

비교 범위는 **타깃 → vmagent의 AZ 간 scrape 전송**입니다. 분할 전 규모와 분할로 줄일 수 있는 양을 대략적으로 비교했습니다.

| 지표 | AS-IS · agent 1대 | TO-BE · AZ별 agent | 예상 감소량 |
|---|---|---|---|
| 하루 AZ 간 전송량 | **약 2TB** | 거의 없음 | **하루 약 2TB** |

대상 타깃을 모두 같은 AZ에서 수집하면 해당 구간의 AZ 간 전송을 거의 없앨 수 있습니다. 수집하는 메트릭의 양과 저장량은 유지하면서, 수집 위치를 바꿔 AZ를 넘는 트래픽을 줄이는 효과입니다.

## 전환에서 드러난 문제: 라벨 변경이 자동 확장까지 이어진다

수집 경로를 나누는 작업이지만, 저장되는 라벨까지 바꾸면 대시보드와 자동 확장 쿼리에도 영향을 줍니다. 실제 전환에서는 수집 방향을 확인하려고 붙인 zone 라벨과 agent별 외부 라벨 차이가 문제를 만들었습니다.

### 같은 타깃이 옛 시리즈와 새 시리즈로 함께 보였다

검증용 라벨을 새로 붙이거나 외부 라벨을 바꾸면 같은 타깃의 메트릭이 새로운 시리즈가 됩니다. 옛 시리즈가 조회 범위에서 빠지기 전에는 둘이 함께 보일 수 있습니다. 이때 단순히 `sum()`으로 더하면 실제 부하는 그대로인데도 값이 커집니다.

전환 중에는 이 현상이 KEDA 트리거에 반영돼 불필요한 증설로 이어졌습니다. 그래서 기존·새 시리즈를 같은 수집 대상 기준으로 묶고, 최근 샘플을 기준으로 읽도록 트리거 쿼리를 보강했습니다. 이 방식도 메트릭의 의미와 라벨에 맞게 확인해야 하며, 서로 다른 대상의 값을 합쳐 버리지 않도록 주의가 필요합니다.

이후 전환에서는 **두 agent의 외부 라벨을 같은 값으로 맞추고 검증용 라벨을 추가하지 않는 것**을 기본으로 삼았습니다. 외부 라벨의 기본값은 agent 리소스 이름을 따라가므로, 그대로 두면 두 agent의 값이 달라집니다. 수집 방향은 vmagent의 타깃 목록과 자체 메트릭으로 확인할 수 있습니다. AZ별로 수집하는 것과 저장되는 시리즈에 AZ 라벨을 새로 넣는 것은 별개의 결정입니다.

### 검증용 라벨 하나도 수신 측 상한에 걸릴 수 있다

기존 라벨이 많던 일부 시리즈는 zone 라벨이 추가되면서 수신 측의 라벨 개수 상한에 걸렸습니다. 수집이 계속되더라도 저장된 라벨 구성이 달라지면, 특정 라벨로 조회하는 쿼리에서 데이터가 사라진 것처럼 보일 수 있습니다.

분할에는 서비스 디스커버리 단계의 Node 메타라벨을 사용하고, 저장되는 라벨의 변경은 최소화하는 쪽으로 정리했습니다. 전환 검증도 타깃의 `up` 상태만 보는 데서 끝내지 않고, 기존 쿼리가 기대하는 라벨로 계속 조회되는지까지 확인해야 합니다.

## 중복·누락과 전송량을 함께 확인한다

수집 대상을 나눌 때는 중복과 누락을 함께 확인해야 합니다.

| 확인 항목 | 확인할 내용 |
|---|---|
| 수집 범위 | 두 agent 사이의 중복·누락, fallback 타깃, down 타깃 |
| 수집량 | scrape와 remote write 총량이 전환 전후 비슷한지 |
| 외부 라벨 | 두 agent의 외부 라벨이 같은 값인지 |
| 검증용 라벨 | 새 라벨이 시리즈 정체성을 바꾸거나 라벨 개수 상한을 넘지 않는지 |
| 자동 확장 쿼리 | lookback 구간에서 옛 시리즈와 새 시리즈를 함께 합산하지 않는지 |
| agent 가용성 | AZ별 실행 노드 여유와 수집 중단 알림이 있는지 |

전환 직후에는 타깃 목록을 대조했습니다. AZ a의 타깃은 새 agent에, AZ c와 fallback 타깃은 기존 agent에 들어가는지 확인하고, 두 목록 사이의 중복과 빠진 타깃을 따로 봤습니다. 전체 타깃 수만 같아도 한쪽에서 빠진 만큼 다른 쪽에서 중복될 수 있으므로, 합계만으로 판단하지 않았습니다.

그다음에는 두 agent의 scrape와 remote write 전송량을 합쳐 분할 전과 비교했습니다. **수집 총량은 비슷하게 유지되고, 그중 AZ 경계를 넘는 양이 줄어야** 의도한 결과입니다. 전송량 감소가 수집 누락 때문은 아닌지 확인하는 과정이기도 합니다.

측정 과정에서는 조회 시점과 구간도 중요했습니다.

- 자동 확장 쿼리는 대시보드 그래프와 별도로 확인했습니다. 그래프의 조회 간격이 길면 전환 중 잠깐 커진 값을 놓칠 수 있어, KEDA가 읽는 instant query 결과를 대조했습니다.
- agent 파드가 교체된 직후에는 짧은 rate와 긴 구간 평균이 다르게 보였습니다. 안정화 뒤 같은 측정 창으로 다시 비교하고, 누적 전송량에서도 같은 방향인지 확인했습니다.
- 과거 전송량을 AZ별로 나눌 때는 이미 사라진 파드·노드도 찾아야 했습니다. 현재 목록만 사용하면 당시의 타깃을 매핑하지 못하므로, 목록의 조회 범위도 측정 기간에 맞췄습니다.

## 원격 저장 경로에는 AZ 간 전송이 남는다

**하루 약 2TB는 scrape 구간에서 줄일 수 있는 AZ 간 전송량**입니다. 원격 저장소로 보내는 remote write와 저장 클러스터 내부 통신은 계속 발생합니다.

새 agent의 출발 AZ가 달라지면 agent → 쓰기 LB 구간에서 AZ를 넘는 전송이 생깁니다. 다만 쓰기 LB가 같은 VPC의 internal ALB라 이 구간에는 요금이 붙지 않습니다. scrape 구간의 감소와 전체 네트워크의 감소는 따로 봐야 합니다. 이번 변경으로 확인한 전체 inter-AZ 트래픽 감소는 약 10%입니다.

| 구간 | 분할 뒤 확인할 점 |
|---|---|
| 타깃 → vmagent | 타깃과 agent가 같은 AZ에 있는지 |
| vmagent → 쓰기 LB | LB 종류와 접속 경로. 같은 VPC의 internal ALB면 AZ를 넘어도 청구되지 않음 |
| LB → ingress → vminsert | 요청이 저장 클러스터 안에서 어느 AZ로 분산되는지 |
| vminsert → vmstorage | 저장 노드 선택과 복제 과정에서 AZ를 넘는 양이 얼마나 남는지 |

수집을 AZ별로 나눠도 뒤쪽 경로가 자동으로 같은 AZ에 맞춰지지는 않습니다. 쓰기 경로를 한 AZ에 모으면 전송은 줄어들 수 있지만 장애 영향이 커질 수 있으므로, 저장 계층에서는 전송량과 가용성을 함께 봐야 합니다.

## 다음으로 볼 것은 scrape 응답 자체의 크기다

AZ 분할은 응답이 이동하는 경로를 바꿉니다. 타깃이 내보내는 응답 크기는 그대로라서, 수집과 파싱에 드는 부하까지 줄이려면 메트릭 자체를 봐야 합니다. 수집 응답을 살펴보니 Istio 사이드카의 히스토그램 버킷과 반복되는 라벨 문자열이 큰 몫을 차지했습니다.

다음 검토 대상은 사용하지 않는 히스토그램 버킷과 중복 정보를 담은 라벨입니다. 다만 수집한 뒤 metric relabel로 버리면 타깃 → agent 전송은 이미 발생한 뒤입니다. 전송량까지 줄이려면 타깃이 내보내는 단계에서 응답을 줄이거나 압축해야 합니다. Istio는 파드 annotation으로 메트릭 응답 압축을 켤 수 있어, 이쪽을 먼저 검증할 계획입니다. 어떤 대시보드·알림이 해당 메트릭을 쓰는지 먼저 확인하고, 라벨을 바꾼다면 앞서 겪은 시리즈 변경 문제도 함께 검증해야 합니다.
