- 모델이 똑똑해지면 모델을 보조하던 절차는 얇아지고 모델을 통제하는 층은 두꺼워진다.
- 도구의 이름·설명·스키마·응답·에러는 API 문서가 아니라 모델의 다음 행동을 정하는 프롬프트 표면이다. MCP는 기능 호출, A2A는 목표 위임이다.

## 발표 배경과 목표

발표자는 작년부터 에이전트, 올해는 하네스라는 말을 일상적으로 쓰면서도 사람마다 떠올리는 개념이 조금씩 다르다는 걸 자주 겪었다고 합니다. 사내 에이전트 아키텍처 스터디에서도 용어 문제가 반복됐습니다. 직접 서베이를 해 보니 같은 개념을 벤더사나 아티클마다 다르게 부르고 있었습니다. 그래서 용어보다 "이 개념이 무엇을 가리키는가"를 맞춰 보는 자리를 만들자는 취지로 밋업을 열었습니다. 정리한 개념이 완전히 맞지는 않을 수 있지만 후속 논의의 출발점이 되길 바란다는 단서도 붙였습니다.

발표가 끝났을 때 청중이 할 수 있게 되길 바라는 것은 아래 둘입니다.

1. 워크플로우와 에이전트를 구분할 수 있다
2. "하네스"가 모델 밖의 어떤 구성요소를 가리키는지 설명할 수 있다

구성은 1장 에이전트(워크플로우와의 경계), 2장 하네스(모델을 감싸는 실행 골격), 3장 도구(에이전트의 행동 범위), 마무리 순서입니다. 원래 90분 슬롯으로 잡았지만 실제 발표는 1시간 5분 남짓에 끝났습니다.

## 1장 · 에이전트 — 워크플로우와의 경계

### 판단 기준: 다음 순서를 누가 정하는가

에이전트를 이야기할 때 워크플로우까지 에이전트라고 부르는 혼동이 잦아서 발표자는 둘을 나란히 놓고 시작합니다. 둘 다 내부에서 LLM을 쓸 수 있습니다. 워크플로우는 원래 파이프라인이라고도 부르던 것이고, LLM을 쓰지 않을 수도 있습니다. 그런데 안에서 LLM을 부른다는 이유만으로 에이전트라고 부르는 경우가 있어 기준을 하나로 좁혔습니다. 지금 상태에서 다음 상태로 넘어갈 때, 코드를 읽어서 다음에 무엇이 실행될지 알 수 있으면 워크플로우이고 코드를 봐도 알 수 없으면 에이전트입니다.

| | 무엇인가 | 다음 순서를 누가 정하나 |
|---|---|---|
| 워크플로우 | LLM 호출과 도구 실행을 미리 정해둔 코드 경로로 엮은 것 | 코드 |
| 에이전트 | LLM이 관측 결과를 보고 다음 행동을 스스로 선택하며 목표까지 반복하는 것 | 모델 |

슬라이드에는 Simon Willison(2025-09)의 한 줄 정의 *"An LLM agent runs tools in a loop to achieve a goal."*이 함께 실렸고, 위 표의 정의는 Anthropic의 *Building Effective Agents*(2024-12)를 따른 것이라고 밝혀 두었습니다.

### 예시: 같은 CS 환불 문의를 두 방식으로

같은 환불 문의를 푸는 시스템 둘을 비교합니다. 차이는 다음 순서를 누가 정하느냐 하나뿐입니다.

| | 워크플로우 | 에이전트 |
|---|---|---|
| 입력 | CS 카테고리(환불) · 상품 선택(티셔츠) · 문의 본문("사이즈가 안 맞아요") | "저 환불하고 싶어요" (카테고리 · 상품 없음) |
| 진행 | ① CS 정책 검색(카테고리로) → ② 상품 정보 조회(상품 ID로) → ③ 프롬프트 조립(정책+상품+본문) → ④ LLM 답변 생성 | 모델이 구매 내역 조회 · CS 정책 검색 · 사용자에게 되묻기 중 무엇을 몇 번 쓸지 매번 고르고(`tool_use` → `tool_result`), 도구 호출이 없으면 종료 |
| 약점 | 예상 밖 케이스. 그린 적 없는 경로는 갈 곳이 없다 | 비용을 예측할 수 없다. 조회 횟수 · 대화 턴이 문의마다 다르다 |

워크플로우의 약점을 발표자는 이렇게 풀었습니다. 사용자가 카테고리를 결제로 잘못 고르면 결제 정책을 가져오는데 본문은 "환불하고 싶어요"입니다. 이때 LLM은 할루시네이션으로 우리에게 없는 정책을 근거로 답할 수 있습니다. 에이전트 쪽에는 최종 답변까지의 경로를 코드로 정의하지 않고 도구만 쥐여 줍니다. 대신 같은 질의가 들어와도 내부 동작이 그때그때 달라질 수 있고, 그래서 디버깅이 무척 어렵다는 점을 약점으로 꼽았습니다.

에이전트 쪽 흐름을 한 단계씩 풀면 이렇습니다. 발표자는 같은 입력이라도 반드시 이 순서를 타는 건 아니며 하나의 예시일 뿐이라고 덧붙였습니다.

| 단계 | 모델의 판단 | 행동 | 관측 (다음 결정의 입력) |
|---|---|---|---|
| ① | 어떤 상품인지 모른다 — 구매 내역부터 본다 | 도구 · 구매 내역 조회 (구매 확정 전 상품) | 3건 — 티셔츠 · 운동화 · 모자 |
| ② | 셋 중 무엇인지는 사용자만 안다 — 되묻는다 | 되묻기 "어떤 상품을 환불하시나요?" | 사용자 "티셔츠요" |
| ③ | 환불 조건을 확인해야 한다 | 도구 · CS 정책 검색 "환불" | 7일 이내 · 미개봉이면 환불 가능 |
| ④ | 주문일 09-12, 오늘 09-17 — 조건 충족, 답할 수 있다 | 답변 "환불 가능합니다. 접수해 드릴까요?" | 도구 호출 없음 → 종료 |

카테고리를 잘못 고른 문의 같은 예상 밖 케이스도 에이전트는 관측을 보고 궤도를 바꿔 처리합니다. 그 대가가 비용 예측 불가입니다.

### 에이전트의 실체는 while 루프

발표자는 에이전트를 간단히 while 루프로 봅니다. 사용자 요청이 들어오면 모델이 도구를 더 부를지 끝낼지를 고릅니다. 도구를 부르면(`tool_use`) 하네스, 곧 런타임이 실행하고, 결과(`tool_result`)를 Context에 붙여 다시 모델로 돌려보냅니다. 도구 호출이 없는 응답이 나오면 루프가 끝나고 최종 응답이 나갑니다.

```
사용자 요청 → [ 모델: 도구를 부를지, 끝낼지 ]
                  │ tool_use              ▲ tool_result (관측을 Context에 붙임)
                  ▼                       │
              [ 도구 실행 — 하네스(런타임)가 실행 ] ─┘
              도구 호출이 없는 응답 → 최종 응답
              최대 턴 · 오류에 닿으면 하네스가 끊는다
```

종료를 모델에만 맡기지 않는다는 점이 2장으로 이어집니다. 설계상 도구 호출이 10번이면 충분하다고 봤는데 모델이 덜 똑똑하거나 지시가 잘못돼 20번, 30번씩 도구를 부를 수 있습니다. 커뮤니티에서 "루프가 터진다"고 부르는 상황입니다. 하네스에서 최대 호출을 10번으로 정해 두면 모델의 판단과 무관하게 10번째에 최종 응답을 내도록 시스템이 강제할 수 있습니다.

### ReAct와의 관계

이 루프를 설명하면 "그거 ReAct 아니에요?"라는 질문을 자주 받는다고 합니다. 구조는 같습니다. 다른 점은 규약을 어디에 두느냐입니다. ChatGPT 초기의 프롬프트 엔지니어링 시절에 가장 널리 채택된 방식이 ReAct였고, 지금은 그 패턴이 유의미하다 보니 모델이 아예 tool calling을 학습했습니다. 모델 비교표에서 tool calling 지원 여부를 표시하는 게 그 흔적입니다. 발표자는 프롬프트 엔지니어링에서 컨텍스트 엔지니어링, 다시 하네스 엔지니어링으로 관심이 옮겨 왔다는 흐름도 함께 짚었습니다.

| | 고전 ReAct (2022) | 현대 Agent Loop |
|---|---|---|
| 규약을 두는 곳 | 시스템 프롬프트에 직접 정의 | 모델이 tool calling을 학습 |
| 형식 | `Thought:` / `Action:` / `Observation:` 텍스트 | `text` / `tool_use` / `tool_result` 구조화된 블록 |
| 종료 신호 | `Final Answer:`가 나오면 끝 | `tool_use` 없는 응답이 나오면 끝 |
| 누가 처리 | 형식은 프롬프트로 약속하고 파싱은 코드가 | 형식은 모델이 학습했고 실행은 런타임이 |

이후 예시는 대부분 Claude Code에서 가져왔습니다. 환불 시스템은 추상적이라 눈에 잘 안 보이기 때문입니다. 발표자는 Codex도 같다고 말합니다. Claude Code에 지침을 주고 최종 답변을 받을 때까지가 루프 하나이고, 그 안에서 Edit·Bash 같은 도구를 부르고 결과를 받는 과정이 반복됩니다. 평소 화면에서 보던 그 흐름이 곧 에이전트 루프입니다.

### 적용 기준: 에이전트가 더 "좋은 것"은 아니다

에이전트가 뭐든 해 줄 것 같으니 분기를 귀찮게 짤 필요 없이 전부 에이전트로 풀자는 생각이 들 수 있고, 발표자도 처음엔 그랬다고 합니다. 작년 밋업에서 했던 말을 그대로 다시 가져옵니다. 화이트보드에 문제 풀이 흐름을 명확하게 그릴 수 있다면 워크플로우가 맞습니다. 불안정한 에이전트를 굳이 쓸 이유가 없습니다. 분기와 예외 케이스가 계속 늘어나 관리가 버거워지면 에이전트를 씁니다.

> 실행 경로를 미리 그릴 수 있으면 에이전트를 쓰지 않는다. 그릴 수 없을 때 — 중간 결과를 봐야 다음이 정해질 때 — 에이전트가 필요하다.

| 워크플로우가 맞는 경우 | 에이전트가 맞는 경우 |
|---|---|
| 단계가 고정되고 매번 같다 | 중간 결과를 봐야 다음 단계가 정해진다 |
| 결과의 일관성 · 사후 추적(감사) 가능성이 중요하다 | 예상하지 못한 상태를 만나 대응해야 한다 |
| 실패 비용이 크고 되돌리기 어렵다 | 검증 수단(테스트 · 비교)이 있어 틀려도 잡을 수 있다 |

### 실무의 형태: Agentic Workflow, 그리고 반대 방향

"그럼 이 문제는 워크플로우로 할래, 에이전트로 할래?"라는 논의가 자주 벌어지지만 발표자는 둘 중 하나를 고르는 문제가 아니라고 봅니다. 프로덕션에서 지배적인 형태는 워크플로우의 안정성과 에이전트의 유연성을 합친 Agentic Workflow입니다. 파이프라인 전체는 워크플로우로 고정하고 판단이 필요한 구간만 에이전트에 위임하며, 이는 Anthropic과 OpenAI 가이드의 공통된 권고라고 슬라이드는 적고 있습니다.

같은 환불 문의를 이 형태로 다시 짜면 이렇습니다.

```
"저 환불하고 싶어요" (카테고리 · 상품 고르지 않음)
  → LLM 의도 분류 (닫힌 집합: 배송 조회 · 환불/교환 · 결제 · 기타 — 코드가 다음을 안다)
      ├ 배송 조회 등 단순      → 워크플로우: 상품 조회 → 답변 (비용 고정)
      ├ 환불 · 교환, 판단 필요 → Agent에 위임: 구매 내역 조회 · CS 정책 검색 · 되묻기
      └ 기타 · 분류 신뢰도 낮음 → 담당자 라우팅 (사람이 답한다)
  → 발송
```

카테고리를 사용자가 고르지 않고 모델이 분류하니 오입력이 사라지고, 애매한 건 담당자에게 갑니다. 비용은 에이전트 갈래에서만 생기므로 어느 문의가 비용을 쓰는지 알 수 있습니다. 발표자의 말로는 이미 발견한 확실한 케이스는 워크플로우로 싸게 처리하고, 판단이 필요한데 아직 조건문으로 굳힐 만큼 케이스를 모으지 못한 것은 에이전트에, 에이전트도 못 풀 것 같은 건 CS 담당자에게 보내는 구성입니다.

포함 관계는 반대로도 성립합니다. 다음 순서를 코드가 소유하는 구간을 워크플로우로 굳혀 도구 하나로 포장하면, 모델은 그 도구를 언제 부를지만 정합니다. 에이전트에게 주어진 "환불 처리" 도구가 겉으로는 도구 하나지만 안에서는 이런 워크플로우가 돕니다.

```
환불 처리 (모델에게는 도구 하나)
  ① 주문·배송 조회
  ② LLM 사유 판정            ← 모델이 고르는 건 여기 한 칸
       ├ 변심   → 반품비 차감
       ├ 하자   → 전액 + 품질 등록
       └ 오배송 → 전액 + 재발송
  ③ 공통 구간: 결제 취소 → 알림 발송 → 원장 기록
  → {"refunded": true, "amount": 28000}   ← 모델이 돌려받는 것은 이 한 줄
```

발표자는 사유 판정도 코드로 만들 수 있으니 예시가 다소 억지스럽다고 인정하면서도, 요점은 에이전트냐 워크플로우냐가 아니라고 정리합니다. 코드로 정할 수 있는 부분과 아직 정할 수 없는 부분을 나누고, 어떻게 조립할지는 시스템의 성격에 따라 정하면 됩니다.

## 2장 · 하네스 — 모델을 감싸는 실행 골격

### 왜 하네스인가

2장의 판단 기준은 "모델은 생각하지만, 하네스가 일하게 만든다"입니다. 발표자가 시스템 설계의 중요성을 처음 체감한 건 Cursor와 Claude Code를 동시에 쓰던 작년이었습니다. 둘 다 같은 Opus 모델이었는데 같은 작업을 시켜도 Claude Code가 더 잘한다고 느꼈습니다. 그때까지는 모델이 전부라고 생각했지만 돌아보니 차이는 모델이 아니라 모델 바깥, 하네스 설계에 있었다는 것입니다.

하네스 엔지니어링의 정의는 찾아볼수록 다 달라서 발표자에게 가장 와닿은 것을 골랐습니다.

> AI 모델 자체의 추론 능력을 제외하고, AI 에이전트가 실제 업무 환경에서 안전하고 안정적으로 실행되도록 주변 환경 · 규칙 · 도구 · 검증 장치를 설계하는 시스템 구축 기술.

스킬 몇 개 추가하는 일이 아니라 시스템 전체를 보는 구축 기술이라는 뜻입니다. 어원인 Harness는 말의 마구·고삐라서 AI의 능력을 억누르는 장치로 오해하기 쉽습니다. 발표자는 그 해석도 절반은 맞다고 봅니다. 똑똑하지만 예측하지 못하게 움직일 수 있으니 이탈을 막는 것은 억누르는 쪽입니다. 다만 순서로 치면 시스템을 올바른 방향으로 유도하는 제어 장치 역할이 먼저이고 이탈을 막는 건 그다음이라고 강조했습니다.

### 하네스 한 장 그림과 Claude Code 실물

하네스 구성요소를 검색해도 마음에 드는 그림이 없어서 발표자가 손으로 그린 것을 AI로 정리한 도식입니다. 중요한 것만 담았고 이보다 더 많은 요소가 있을 수 있다고 했습니다. 같은 그림에 Claude Code의 실물을 겹치면 오른쪽 열이 됩니다. 발표자에 따르면 Claude Code는 스스로를 agentic harness라고 부르기도 합니다.

| 하네스 요소 | 일반 개념 | Claude Code 실물 |
|---|---|---|
| State | 현재값으로 덮어쓴다 (Context에는 일부만) | 작업 목록 (plan mode) |
| 대화 이력 | 원본이 붙는다 | 트랜스크립트 `.jsonl` |
| Long-term Memory | 추려서 남긴다 | 메모리 디렉토리 |
| Domain Knowledge | 사람이 미리 써둔다 | `CLAUDE.md` · 스킬 |
| Context | 이번 호출에 필요한 것만. 요소가 아니라 매 호출 구성되는 뷰 | 루프마다 필요한 Context만 구성 |
| 루프 | 관측 → 결정 → 실행 반복 | 세션 안에서 도구 호출이 이어지는 것 |
| 도구 | 읽기 · 검색 · 실행 · 변경 = 행동 공간 | Read · Edit · Grep · Bash · Agent 기본 도구 + 사용자가 연결한 MCP 도구 |
| 권한 | 자율 / 승인 | auto · accept 모드, 도구별 실행 권한 |
| 상한 | 턴 · 비용 · 시간 | 오류 반복 시 루프 중단, Context Window |
| 관측 | 무엇을 왜 했는지 기록 | 트랜스크립트 · 훅 |

모델 자체는 하네스에서 제외합니다. 도구에서 발표자는 MCP를 "MCP라는 도구"라기보다 사용자가 커스텀 도구를 넣을 수 있는 프로토콜을 제공하는 것으로 보는 편이 정확하다고 짚었습니다.

Context는 하네스 엔지니어링 이전에 주목받던 개념입니다. 모델 입력에는 언제나 Context라는 텍스트가 들어가고, Context Window가 계속 늘어나더라도 유한하니 이번 턴에 필요한 것만 정제해서 채웁니다. 그 일이 컨텍스트 엔지니어링입니다. 시스템 프롬프트, 사용자 질문, AI의 이전 답변 말고 Context를 채우는 재료가 저장 계층 넷이고, Claude Code는 이것을 사용자 로컬 파일로 외부화해 둡니다.

- State — plan mode에서 세운 네 단계 중 두 번째까지 했다는 사실을 저장해 두고 "1·2 완료, 3·4 남음"을 Context에 다시 넣는다. 사람처럼 중간에 흐트러져 3단계를 건너뛰고 끝내 버리는 일을 막는다
- 대화 이력 — 질문·답변·도구 실행과 결과를 JSON Lines 트랜스크립트로 남긴다. 실수로 터미널을 꺼도 이어갈 수 있다. 모델은 매번 똑같이 행동하지 않으니 기억에 기대 다시 묻고 답하는 방식으론 복원이 안 된다
- Long-term Memory — 과거 세션 트랜스크립트를 바탕으로 "이 사용자가 이걸 하지 말라고 했다" 같은 것을 주기적으로 추려 메모리 파일로 만든다. 사람이 `CLAUDE.md`에 적는 게 아니라 에이전트가 알아서 장기 기억화한다
- Domain Knowledge — `CLAUDE.md`와 스킬. 모델이 학습할 수 없는 사내 정보(발표자의 예: 네이버 내부의 N3R, 커넥트)를 주지 않으면 검색부터 해 보다가 엉뚱한 말을 한다. 그 플랫폼이 무엇이고 어떻게 쓰는지 스킬로 쥐여 준다

여기서 발표자는 분류 하나를 원자료와 다르게 했다고 밝힙니다. Claude Code 문서는 `CLAUDE.md`를 구현상 "메모리"로 분류합니다. 세션 밖에서 살아남아 매 실행의 컨텍스트에 다시 주입되기 때문입니다. 하지만 에이전트 시스템 설계 관점에서 `CLAUDE.md`가 제공하는 건 프로젝트 규칙·작업 절차·도메인 지식이므로 지속성 있는 지식·지침 계층, 곧 Knowledge로 묶는 편이 더 정확하다고 봤습니다.

저장 계층과 Context, 루프, 도구는 에이전트가 말을 찰떡같이 알아듣고 움직이게 하는 쪽이고, 그 바깥을 감싸는 권한·상한·관측은 제어 장치입니다. 상한에 대해 발표자는 Context Window가 일정 수준(대략 80% 이상)을 넘으면 auto compact를 하거나, 같은 오류를 반복하며 도구를 계속 불러 토큰과 비용을 태우는 루프를 끊는 최소한의 제어권을 예로 들었습니다.

### 없으면 어떻게 되는가

있으면 좋다는 설명만으로는 와닿지 않으니 발표자는 요소마다 "없으면 어떻게 되는가"를 짚었습니다. 이 슬라이드는 영상에 잡히지 않아 전사로만 정리했습니다.

| 빠진 요소 | 생기는 일 |
|---|---|
| 루프 | 한 번 호출하고 끝난다. 텍스트만 내뱉고 요청한 작업을 끝내지 못한다 |
| 도구 | 말만 한다. 옛날 ChatGPT처럼 아무 행동도 못 한다 |

| Knowledge | 내 환경에 맞는 지식이 없어 그럴듯하게 틀린 판단을 한다 |
| 권한 | 배포, 위키 문서 생성 같은 되돌릴 수 없는 행동을 에이전트가 마음대로 반복할 수 있다 |
| 상한 | 루프 중단 조건이 없어 무한 루프에 빠지고 토큰과 비용이 계속 나간다 |

발표자의 정리는 하네스 요소를 전부 갖추라는 게 아니라 그때그때 필요한 것을 가져다 쓰면 된다는 것입니다.

### Claude Code 설계에서 가져올 것 세 가지

2026년 3월 Claude Code 소스가 유출됐을 때 많은 개발자가 리버스 엔지니어링을 했고, 발표자도 그때 본 것 중 설계 패턴 셋을 골랐습니다. 슬라이드 각주도 유출 소스를 분석한 자료에서 설계 패턴 일부만 가져왔다고 밝혀 둡니다.

첫째는 전용 도구입니다. 범용 `Bash` 하나로도 `cat api.py`로 파일은 읽을 수 있습니다. 하지만 코딩 어시스턴트는 읽은 다음 고치는 게 일인데 `cat` 출력엔 줄번호가 없어 편집 위치를 짚지 못합니다. `grep`·`find` 출력은 잘리고, `sed`는 검증 없이 파일을 덮어쓰고, 권한도 "Bash 한 덩어리"라 세분화가 안 됩니다. 그래서 `Bash`는 남기되 자주 쓰는 동작을 전용 도구로 따로 만들었습니다.

| 동작 | 전용 도구 | 하는 일 |
|---|---|---|
| 읽기 | `Read` | 줄번호를 붙여 준다 |
| 검색 | `Grep` · `Glob` | 출력을 다듬어 준다 |
| 수정 | `Edit` | 먼저 Read 했는지, 바꿀 문장이 하나뿐인지 검사한다 |
| 실행 | `Bash` | 테스트 · 빌드용으로 남긴다 |

도구만 만든 게 아니라 시스템 프롬프트에 언제 무엇을 쓸지도 적어 두었습니다. 파일은 cat 말고 Read, 검색은 grep 말고 Grep, 수정은 sed 말고 Edit, Bash는 실행에만. 화면에서 늘 보던 아래 장면이 그 결과입니다. 모델이 알아서 좋은 도구를 고른 것처럼 보이지만 하네스가 도구를 나눠 만들고 선택 기준을 주입한 결과라는 게 발표자의 해석입니다.

```
● Edit(src/app/api.py)
  ⎿ Error: File has not been read yet. Read it first before writing to it.
```

둘째는 의도와 실행 사이의 통제 층입니다. 이 장치가 없으면 모델의 의도가 곧 시스템 변경이 됩니다. `rm -rf`나 `git push --force` 같은 비가역 행동을 막을 지점이 없고, 읽기 10번을 한 줄로 서서 기다립니다. Claude Code는 권한 판단을 계층화했습니다. 명시적 deny rule → 명시적 allow rule → 명령 위험도 분류 → 애매하면 사용자 승인 순서입니다. 실행 방식도 도구 성격을 따릅니다. 읽기·검색은 병렬, 파일 수정은 섞일 수 있으니 순차, 서브에이전트에는 필요한 도구만 줍니다. 결국 도구 정의에 실행 정책이 함께 붙어 있습니다.

> 도구 = 스키마 + 읽기/쓰기 여부 + 병렬 가능 여부 + 권한 정책

셋째는 세션이 반드시 깨질 수 있다는 전제입니다. 이 구간의 슬라이드는 영상에 없어 전사로만 정리했습니다. Context Window를 넘기면 세션이 죽으니 창이 어느 정도 차면 대화와 도구 결과를 auto compact합니다. 파일을 고치는 도중 Esc로 끊고 "수정하지 마"라고 하면 실행 중이던 수정이 원래대로 돌아오는데, 수정 전에 체크포인트를 두기 때문입니다. 어제 끝내지 못한 작업을 resume으로 이어갈 수 있는 것도 트랜스크립트를 밖으로 빼 두었기 때문입니다. 하나의 세션에 모든 걸 걸지 않고 다 외부화해서 언제든 이어가고 되돌릴 수 있게 한 점을 발표자는 배울 점으로 꼽았습니다.

2장 전반부의 정리 문장은 이렇습니다. 좋은 시스템은 좋은 모델에서 나오지 않습니다. 모델이 좋아지면 시스템도 좋아지겠지만, 같은 모델을 두고 하네스를 어떻게 구성하느냐에서 품질이 갈립니다.

### 얇아지는 것과 두꺼워지는 것

"모델이 똑똑해지면 하네스는 얇게 가져가야 한다"와 "하네스 엔지니어링을 해야 한다"는 말을 둘 다 들으면 무엇을 얇게 하라는 건지 헷갈립니다. 발표자는 이것을 Claude Code·Codex를 쓰는 사용자 입장에서 설명합니다.

예전 모델이 덜 똑똑해서 저지른 실수 때문에 `CLAUDE.md`나 `AGENTS.md`에 절차가 쌓였습니다. 바로 고치다 틀리고 오류를 놓치니 판단 기준을 계속 넣었던 것입니다. 모델이 똑똑해지면 이런 절차는 필요 없어집니다. 오히려 똑똑한 모델이 절차를 충실히 따르느라 토큰을 낭비하고, 더 좋은 결과를 낼 수 있었는데 예전과 다를 바 없는 결과가 나옵니다. 새 모델로 바꿨는데 비슷하다고 느꼈다면 하네스를 정리할 때라는 신호입니다. 슬라이드는 이 비교를 "(가상 사례)"로 표시했습니다.

| 전 — 모델의 부족한 판단을 절차로 보완 | 후 — 목표와 완료 기준을 주고, 방법은 맡김 |
|---|---|
| 모든 코드 수정 전에 계획을 작성하라 | 문제를 해결하고, 관련 테스트로 검증하라 |
| 원인 후보를 반드시 세 개 제시하라 | 공개 API 호환성을 유지하라 |
| 구현 에이전트와 검토 에이전트를 따로 실행하라 | 요구사항이 모호하면 먼저 확인하라 |
| 검토 결과를 반영한 뒤 다시 검토하라 | |
| 바로 고쳐서 틀리길래 · 오류를 놓치길래 그때 붙인 것 | 남는 것은 프로젝트 고유의 요구와 권한 경계. 모델이 똑똑해져도 사라지지 않는다 |

"새 모델이니 다 지우자"가 아닙니다. 절차 없이도 잘하는지 확인하고 불필요해진 것을 걷어내는 게 얇게 가져가기입니다.

실제로 우리가 하네스를 얇게 가져가 본 예로 발표자는 GitHub MCP를 듭니다(이 슬라이드도 영상에 없음). MCP가 처음 나왔을 때 다들 GitHub MCP를 붙였지만 지금은 `gh` CLI로 넘어간 사람이 많습니다. GitHub MCP는 이슈 생성·목록·조회·코멘트처럼 목적별로 도구를 잘게 나눠 두었고, 도구마다 이름·설명·입력 스키마가 Context를 차지하는데 그게 몇십 개였습니다. 당시엔 모델이 명령을 구성하고 결과를 처리하는 걸 어려워해서 작업별로 정해진 입력을 받는 도구가 필요했습니다. 지금은 `CLAUDE.md`에 "Git 작업은 gh CLI로 한다"고만 적어 두면 모델이 범용 도구인 Bash로 CLI 사용법을 스스로 읽고 명령을 조립합니다. 많은 전용 도구에서 범용 도구 하나와 CLI로 옮겨 간 것이 우리가 공통으로 겪은 "얇아진 하네스"입니다.

그렇다고 하네스가 계속 얇아지기만 하는 건 아닙니다. 슬라이드가 인용한 Anthropic의 *Improving Fable 5's biology safeguards*(2026-08-07)에 따르면 Fable 5는 일부 생물학 과제에서 전문가를 능가해서, 출시 때 거의 모든 생물학 질의를 차단했습니다.

```
생물학 관련 요청 → 안전 분류기 (위험 · 이중 용도인가 판별 — 모델 밖, 하네스 그림의 권한 칸)
                    ├ 허용          → Fable 5 가 답한다 (일상 건강 · 교육 질문)
                    └ 차단 → fallback → Opus 5 로 우회해 답한다 (바이러스학 · 독성학 · 분자 설계)
```

출시 뒤에는 분류기 규칙을 다시 써서 오탐을 85% 줄였습니다. 두꺼운 층도 측정하고 고친다는 뜻입니다. 발표자는 개인 경험도 덧붙였습니다. 데이터 관련 도구를 쓸 때 Fable을 골라도 자동으로 Opus로 바뀌는 일을 겪었다고 합니다(본인만 겪은 것인지는 모르겠다는 단서와 함께). 분류기 자체도 처음엔 두껍게 가다가 의도를 제대로 파악해 정말 악의적인 경우만 걸러내도록 점점 얇게 다듬는 연구를 Anthropic이 하고 있다고 전했습니다.

> 얇아지는 것은 모델을 보조하던 절차, 두꺼워지는 것은 모델을 통제하는 층이다. "얇게 가져가라"도, "하네스 엔지니어링을 해야 한다"도 맞다. 말하는 대상이 서로 다를 뿐이다.

## 3장 · 도구 — 에이전트의 행동 범위

### 도구 집합이 곧 행동 범위

원래는 에이전트와 하네스만 다룰 생각이었는데 사내에서 도구에 대한 의견이 생각보다 많아 하네스 그림의 도구 칸만 따로 떼어 냈다고 합니다. 3장의 판단 기준은 이렇습니다.

> 도구의 이름 · 설명 · 스키마 · 응답 · 에러는 API 문서가 아니라 모델의 다음 행동을 정하는 프롬프트 표면이다.

에이전트가 할 수 있는 행동의 공간이 이 한 칸에서 정해지고, 여기서 돌아오는 것이 다음 판단의 근거가 됩니다. Claude Code에 Read만 줬다면 "이 파일의 이 코드를 이렇게 바꿔 보세요"라고 텍스트로만 답했을 겁니다. 옛날 ChatGPT처럼요. Edit을 줬기 때문에 실제로 파일을 고칠 수 있습니다.

| | 도구 집합 A — 조회만 | 도구 집합 B — 조회 + 실행 |
|---|---|---|
| 도구 | 구매 내역 조회 · CS 정책 검색 | 구매 내역 조회 · CS 정책 검색 · 환불 처리 |
| "환불하고 싶어요"의 결과 | "7일 이내 미개봉이라 환불 가능합니다" | "환불 접수했습니다 · 3영업일 내 입금됩니다" |
| 어디까지 | 말까지. 아무리 정확해도 처리되지 않는다 | 실행까지 |

모델을 더 똑똑하게 만들어도 없는 행동은 생기지 않습니다. 그래서 발표자는 AI로 문제를 푸는 제품을 만들 때 어떤 문제를 풀지 정한 다음 필요한 도구를 리스트업하는 것을 첫 번째 일로 꼽습니다.

### 호출자가 모델이면 무엇이 달라지는가

구매 내역 조회나 환불 처리는 대개 이미 사내 API로 있습니다. 그러면 API를 감싸고 설명과 입력 스키마만 주면 도구 아니냐는 질문이 나옵니다. 발표자는 그렇게 해도 돌아가니 일부는 맞다고 인정합니다. 차이는 호출자에 있습니다. API는 사람이 명세를 읽고 쓴 코드가 부르고, 한 번 맞게 개발하면 스펙이 바뀌지 않는 한 문제가 없습니다. 에이전트의 도구는 모델이 호출자이고, 모델은 도구 응답이 무엇을 뜻하는지 잘 모릅니다. 발표자는 "에이전트 도구의 호출자는 모델"이라는 점을 항상 명심하자고 강조합니다.

모델이 보는 Context에는 도구 명세(`get_purchase_history(from, to)`, `search_policy(q)`, `process_refund(order_id, reason)`), 대화("환불하고 싶어요"), 그리고 부를 때마다 쌓이는 도구 응답이 함께 들어 있습니다.

1. 도구 명세를 읽고 필요한 도구를 고른다
2. 성공이든 실패든, 응답이 다음 행동을 정한다
3. 명세도 응답도 컨텍스트를 차지한다 — 유한하다

그래서 도구는 두 층입니다. 기존 API를 그대로 감싸면 아래 코드 층까지는 생기지만 위 텍스트 층은 설계하지 않은 채 남습니다.

| 층 | 무엇 | 역할 |
|---|---|---|
| 텍스트 층 — 모델이 읽는다 | name · description · input_schema · response · error | 모델이 도구를 고르고 · 인자를 채우고 · 실패에서 복구하는 근거 |
| 코드 층 — 실제로 동작한다 | 구현 · 기존 REST API 호출 · DB 조회 | 기존 API를 감싸면 여기까지는 생긴다 |

발표자가 특히 중요하게 보는 것은 response와 error입니다. 모델은 에러를 보고 다음 행동을 정하기 때문입니다. 예를 들어 사용자가 "최근 3개월 구매 내역을 확인해줘"라고 했는데 이 도구는 리소스 문제로 한 번에 최대 7일만 조회할 수 있다고 가정합니다.

| 응답 | 모델의 반응 |
|---|---|
| `{ "error": "E104" }` | 같은 요청을 다시 부르거나 "실패했습니다"로 끝낸다. 무엇을 바꿔야 하는지 알 수 없다 |
| `{ "error": "DATE_RANGE_TOO_LARGE", "message": "조회 기간을 7일 이하로 나누어 다시 호출하세요." }` | 기간을 7일씩 나누어 다시 부른다. 응답만 읽고 스스로 고친다 |

기존 API라면 개발자가 문서를 찾거나 담당자에게 물어 `E104`의 뜻을 알아내고 예외 처리를 짰습니다. 에이전트 도구에서는 복구에 필요한 조건을 응답이 직접 전달해야 하고, 발표자는 거기까지가 도구 설계라고 봅니다.

### 도구의 위층을 설계할 때 묻는 다섯

| 질문 | ✗ 이렇게 주면 | ✓ 이렇게 주면 |
|---|---|---|
| ① 경계 — 도구 하나의 크기 | `get_user_id` → `get_calendar_id` → `post_event`. 순서와 의존성을 모델이 매번 맞춘다 | `create_event(user, when)`. 작업 단위 하나, 셋은 안에서 부른다 |
| ② 선택 — 언제 이 도구를 쓰는가 | `get_data()` · `fetch_data()` · `load_data()`. 비슷한 것 중 아무거나 고른다 | `get_purchase_history(from, to)`. 이름·설명만 읽고 고를 수 있다 |
| ③ 복구 — 실패하면 무엇을 고치나 | `400 Bad Request`. 추측으로 재시도하거나 포기한다 | `DATE_RANGE_TOO_LARGE` · "7일 이하로 나누어 다시 호출". 응답만 읽고 스스로 고친다 |
| ④ 출력 — 판단할 만큼만 | 5,000건 전체 · `{"st": 3}`. 창을 채우거나 뜻을 모른다 | limit · 필터 · `{"status": "shipped"}`. 필요한 만큼만, 읽히는 값으로 |
| ⑤ 부작용 — 다시 불러도 안전한가 | `create_order()` ×2. 재시도가 중복 실행된다 | `idempotency_key` · `{"applied": "partial"}`. 같은 키는 한 번만, 일부 반영을 알린다 |

경계에 대한 발표자의 단서는 이렇습니다. 사용자 ID·캘린더 ID 조회가 일정 등록에만 쓰이고 다른 액션에서 재사용되지 않는다면 굳이 원자적으로 나눌 필요가 없습니다. 나누면 순서를 매번 모델이 추론해야 하고 그만큼 토큰을 씁니다. 선택은 가장 흔한 문제라고 했습니다. 발표자 스스로도 함수 이름을 불친절하게 짓는 습관이 있었다고 털어놓는데, get/fetch/load가 나란히 있으면 모델은 하나씩 불러 보며 토큰을 낭비합니다. 출력에서는 약어 응답을 받으면 모델이 대충 유추해 해독하고 그게 다음 행동에 영향을 준다는 점을, 부작용에서는 쓰기 도구가 중간에 실패했을 때 재시도해도 안전한지를 기존 API 설계처럼 따져야 한다는 점을 짚었습니다.

이 다섯 가지는 발표자 개인의 의견이 아니라 Anthropic의 *Writing effective tools for AI agents*(2025-09-11)에서 가져온 것이라고 밝혔습니다. 그 글에 따르면 Anthropic은 도구 하나를 평가셋으로 측정하며 릴리스 때마다 고칩니다.

```
도구 초안 (먼저 대충 만든다)
 → 평가 태스크 생성 (실제 업무 기반 수십 개)
 → 에이전트 루프로 실행 (API를 직접 돌린다)
 → 트랜스크립트 분석 (어디서 막혔나)
 → 도구를 고친다 (설명 · 스키마 · 응답)
 → 처음으로 반복 — 여기서 나온 관찰이 다음 수정이 된다
```

> "Even small refinements to tool descriptions can yield dramatic improvements." — 도구 설명을 조금만 다듬어도 결과가 크게 달라진다.

도구 정의는 한 번 써서 배포하면 끝나는 문서가 아니라 측정하고 고치는 대상입니다. 하네스와 같은 논리로, 모델이 덜 똑똑하던 시절 10줄, 20줄씩 쓰던 도구 설명도 모델이 똑똑해지면 얇아져도 됩니다.

### 도구 계약: 스키마에 실행 정책을 붙인다

2장에서 본 Claude Code의 도구 컨트랙트를 우리 도구에도 적용하자는 제안입니다. 이름·설명·응답·에러 위에 실행 정책을 붙여 두면 나중에 권한을 제어할 때 편합니다. 슬라이드에는 필수적인 것만 담았습니다.

```
tool: process_refund(order_id, reason)
  고객의 상품 환불 요청을 처리한다 — 결제 취소 · 알림 발송
  ─ 텍스트 층 (3-1에서 다룬 것): name · description · input_schema · response · error
  읽기 / 쓰기  — write
  병렬 가능    — no
  권한         — requires approval
```

발표자는 병렬 가능 여부를 yes/no로만 두지 말고 동시에 몇 개까지 부를 수 있는지까지 계약에 담으면 좋겠다고 덧붙였습니다. 계약을 어떻게 관리하느냐에 따라 필요한 메타데이터는 더 늘어날 수 있다고 봤습니다.

### MCP — 도구를 만드는 자리가 조직 쪽으로

MCP와 MCP 도구를 헷갈려 하는 사람이 많아서 AI 시스템 설계 관점으로 다시 정리합니다. 사내에서 진행 중인 과제가 아니라 예시라고 발표자는 밝혔습니다.

쇼핑 어시스턴트와 고객센터 어시스턴트라는 에이전트 둘이 같은 도구를 필요로 하고, 그 기능은 이미 구매·환불·배송 조직별 API로 있습니다. MCP가 없으면 각 에이전트 조직이 API를 감싸고 설명과 입력 스키마를 달아 직접 관리합니다. 구매 조직의 API가 바뀌면 두 에이전트 쪽에서 각각 고쳐야 합니다. MCP를 두면 조직마다 MCP 서버를 운영하며 도구를 만들고 설명을 관리하고 응답을 제어합니다. 에이전트는 어떤 MCP를 가져다 쓸지만 판단합니다.

```
쇼핑 어시스턴트 (MCP Client)  ─┬─ 구매 조직 MCP Server ── 구매 내역 조회 도구 → 구매 REST API
고객센터 어시스턴트 (MCP Client) ┼─ 환불 조직 MCP Server ── 환불 처리 도구   → 환불 REST API
                               └─ 배송 조직 MCP Server ── 배송 조회 도구   → 배송 REST API
클라이언트 2 + 서버 3 → 선은 여섯 개 그대로. 줄어든 것은 조합마다 다시 만들던 래퍼다
```

도구를 만들고 설명을 관리하는 자리가 쓰는 쪽에서 가진 쪽으로 옮겨 갑니다. 구매 API가 바뀌면 구매 조직이 자기 서버만 고칩니다. 에이전트를 만드는 조직과 API를 가진 조직이 다른 경우가 많으니 이 구조가 맞아떨어집니다.

### MCP와 A2A — 결과를 기대하는가, 판단을 기대하는가

발표자에 따르면 Anthropic이 MCP를 내고 화제가 되자 Google이 A2A 프로토콜을 내놓았고, 둘을 비슷한 것으로 보는 경우가 있습니다. 길게 다루지는 못하고 짧게 짚었습니다. 같은 요청 "배송이 너무 늦는데, 취소하고 환불받을 수 있을까?"를 넘겨도 상대에게 기대하는 것이 다릅니다.

| | MCP | A2A |
|---|---|---|
| 성격 | 기능 호출 | 목표 위임 |
| 실행 경로 소유 | 호출하는 에이전트 | 위임받은 에이전트 |
| 메시지 | `tools/call` → 결과 (스키마대로) | `message/send` → status · artifact |
| 넘기는 것 | `get_delivery_status(order_id)` "이 주문의 배송 상태를 조회해줘" | "취소·환불이 가능한지 확인하고, 가능하면 동의를 받아 진행해줘" |
| 기대하는 것 | 기능 실행 | 업무 수행. 되묻고 · 판단하고 · 도구를 쓴다 |
| 흐름 | 결과가 A의 루프로 돌아와 A가 다음을 정한다 | A는 기다린다. B는 자기 루프 · 자기 도구로 working → input-required → completed |

A2A의 상대는 자기 도구와 자기 루프, 자기 컨텍스트를 가진 별도의 에이전트입니다. 위임한 쪽은 판단 결과만 받고, 에이전트 B가 어떤 생각과 과정을 거쳐 결론을 냈는지는 볼 수 없습니다. 그래서 발표자는 정말 믿고 맡길 수 있는 작업에만 A2A를 쓰는 게 맞다고 봅니다.

## 마무리 — 설계 질문 넷과 세 문장

발표자가 에이전트 시스템을 설계할 때 들고 가라고 남긴 질문입니다. 발표에서는 짧게 넘기고 자료를 사내 위키에 올려 두었다고 했습니다.

- 이 문제의 실행 경로를 지금 순서도로 그릴 수 있는가? 그릴 수 있다면 왜 에이전트가 필요한가?
- 에이전트에 맡기는 구간과 코드가 고정하는 구간의 경계를 어디에 두는가?
- 이 에이전트가 풀 수 있는 문제의 범위, 곧 도구 집합을 명시적으로 그려봤는가? 그 범위 밖의 문제를 만나면 어떻게 되는가?
- 하네스 그림에서 지금 비어 있는 칸은 무엇인가? 비어 있으면 그 자리에서 무슨 일이 생기는가?

오늘의 세 문장은 이렇습니다.

> 에이전트는 모델이 다음 행동을 선택하는 시스템이다.
> 실행 경로를 미리 그릴 수 있으면 에이전트를 쓰지 않는다.
> 모델은 생각하지만, 하네스가 일하게 만든다.

말로 풀 때 발표자는 두 번째 문장에 "비용 측면에서"를 붙였고, 세 번째 문장에는 적당히 좋은 모델이 필요하긴 하지만 하네스 설계에도 관심을 가졌으면 한다는 말을 더했습니다. 자신의 정리가 청중이 이해하던 것과 다를 수 있다며 피드백을 청했고, 발표에서 뺀 부분은 텍스트로 풀어 위키에 공유하겠다고 하며 마쳤습니다.
