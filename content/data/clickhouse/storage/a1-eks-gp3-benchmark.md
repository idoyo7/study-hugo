# 부록 · EKS 범용 노드와 gp3에서 잰 ClickHouse 1억 행 실측

본편 [스토리지 아키텍처 — 로컬 NVMe(i7i/i8g)]({{< relref "/data/clickhouse/storage/02-storage-local-nvme.md" >}})는 로컬 NVMe를 데이터 디스크로 두는 구성을 다룹니다. atomai의 `kubernetes-docs`에는 정반대 조건에서 잰 글이 있습니다. 4 vCPU 범용 노드 한 대와 기본 설정 gp3 100GiB에 Kubernetes 로그 1억 행을 넣고, 적재 속도와 압축률, 쿼리 시간을 잰 글입니다.

디스크 종류가 달라서 이 글의 시간 수치를 본편의 NVMe 수치 옆에 그대로 놓을 수는 없습니다. 압축률과 읽은 행 수처럼 디스크와 무관한 수치는 비교에 쓸 수 있습니다. 본문은 그 구분에 따라 쓰고, 가져온 수치는 모두 atomai 문서가 보고한 값입니다. 우리가 다시 잰 값이 아닙니다.

근거 표기 — `✓` 원문 직접 확인 · `Ⓥ` 저자 주장 · `Ⓑ` 벤치마크 수치 · `?` 미확인. 각 절 끝의 '근거와 측정 조건'에 조건과 세부 수치를 모았습니다.

## 1. 무엇을 어떤 조건에서 쟀는가

노드는 m5.xlarge(4 vCPU, 16GiB) 한 대이고, 벤치마크 파드만 올렸습니다. 볼륨은 EBS gp3 100GiB를 3,000 IOPS, 125MiB/s 기본값으로 붙였습니다. ClickHouse는 24.8.14.39이며 설정은 기본값입니다. 데이터는 반복되는 템플릿에 가변 필드를 섞어 만든 합성 로그 1억 행이고, 7일치 타임스탬프에 ERROR 비율은 0.8%입니다.

이 합성 데이터에는 압축 수치를 읽을 때 걸리는 단순화가 하나 있습니다. 네임스페이스가 10종이고 네임스페이스마다 파드 이름이 하나뿐이라, pod 컬럼의 값이 모두 10종입니다. 원문도 이 컬럼의 압축률이 실제 클러스터보다 낙관적이라고 밝혔습니다.

원문의 대표 수치는 다음과 같습니다.

| 항목 | atomai 문서의 보고값 |
|---|---|
| 적재(서버 내부 생성·삽입) | 1억 행 106.7초, 약 94만 행/초 |
| 압축 크기, LZ4 기본 | 15.37GiB에서 7.82GiB (1.97배) |

## 2. 적재 속도

106.7초에 1억 행이면 초당 약 94만 행입니다. 서버 안에서 `numbers_mt`로 행을 만들어 바로 `INSERT … SELECT`로 넣은 값이라, 네트워크 전송과 텍스트 파싱 비용이 빠져 있고 행을 만드는 CPU 비용은 들어 있습니다. 원문은 이 값이 외부 수집 처리량의 상한이 아니라고 적었습니다. 조건은 `max_threads = 3`, `max_insert_threads = 2`였고 결과로 파티션 7개, active part 36개가 남았습니다.

압축 후 크기를 경과 시간으로 나누면 약 75MiB/s지만, 원문은 이것을 EBS 쓰기 처리량의 계측값으로 보지 않았습니다. 페이지 캐시와 writeback, merge 비용이 섞여 있어서입니다.

이 수치는 본편과 직접 비교할 수 없습니다. CPU가 3.5 vCPU로 제한된 환경의 값이고, 디스크 처리량의 영향을 분리해 재지도 않았습니다. 본편이 말하는 NVMe 쓰기 대역과 같은 축에 놓지 말고, 소박한 환경의 서버 내부 경로 기준값 정도로 읽는 편이 안전합니다.

## 3. 코덱별 압축률

압축률은 디스크 종류와 상관없이 데이터와 스키마, 코덱이 정합니다. 그래서 이 부록에서 본편과 가장 쉽게 맞춰 볼 수 있는 부분입니다. 기본 LZ4에서 전체는 1.97배였고, 컬럼별로 보면 격차가 큽니다. 정렬 키 첫 컬럼인 namespace는 95.7MiB가 489KiB로 줄어 201배가 나왔습니다. 반대로 32자 hex 문자열인 trace_id는 3.07GiB가 3.08GiB가 되어 거의 줄지 않았고, 전체 7.82GiB의 39.4%를 차지했습니다.

같은 데이터를 `CODEC(ZSTD(3))` 테이블에 다시 넣으면 4.16GiB가 되어 LZ4보다 47% 작았습니다. 대신 CPU 비중이 큰 풀스캔은 2.63초에서 4.9초로 1.9배 느려졌습니다. 원문은 최근 데이터에 LZ4, 오래된 파티션에 TTL로 ZSTD 재압축을 거는 조합을 검토 대상으로 제시했습니다. 본편이 다루는 hot NVMe와 cold 분리와 같은 방향의 발상입니다.

다만 이 비율을 용량 계획에 옮길 때는 데이터 형태를 봐야 합니다. 원문이 직접 인정했듯 pod 컬럼의 236배는 합성 데이터 탓에 부풀었고, trace_id는 최악에 가깝습니다. 코덱 비용 쪽의 1.9배 느려짐은 CPU에 묶인 수치라서 압축률과 다르게 취급합니다.

## 4. 쿼리 성능과 인덱스

쿼리는 mark·uncompressed 캐시를 비운 뒤 `min_bytes_to_use_direct_io=1`로 페이지 캐시를 우회한 요청 1회와, warm 3회 중 최솟값을 기록했습니다.

디스크와 무관하게 읽을 수 있는 쪽은 읽은 행 수입니다. 정렬 키 범위로 좁혀지는 1시간 창 count는 결과가 59,916행인데 실제로 읽은 행은 1억 중 16,385행(0.016%)이었습니다. 키 범위에 완전히 들어가는 granule은 인덱스만으로 세고 양끝 granule만 풀어 읽는 최적화가 쓰였다고 원문이 설명합니다. 이 동작은 스토리지가 로컬 NVMe여도 같으므로 본편에서 설계한 정렬 키에도 같은 원리가 적용됩니다. 원문은 `EXPLAIN indexes = 1`과 실제 `read_rows`로 확인하라고 권합니다.

bloom filter skip index는 trace_id 점 조회를 1.13초에서 0.036초로 줄였습니다. 읽은 행이 1억에서 108만으로, 읽은 데이터가 3.82GiB에서 42.6MiB로 줄었고 인덱스 크기는 119.7MiB(테이블의 1.5%)였습니다. 행 수와 인덱스 크기는 스토리지와 무관한 값이고, 시간 수치는 이 CPU와 페이지 캐시 상태의 값입니다.

시간 수치는 디스크에 묶여 있습니다. 같은 풀스캔이 캐시에서는 2.63초인데 Direct I/O 요청에서는 31.5초였습니다. message 컬럼 약 4GiB를 31.5초에 읽은 것이므로 약 130MiB/s이고, gp3 상한 125MiB/s와 이 인스턴스의 EBS 기본 대역(1,150Mbps, 약 137MiB/s) 사이에 걸려 있습니다. 원문도 두 한계가 너무 가까워 어느 쪽이 먼저 걸렸는지 가릴 수 없다고 적었습니다. 본편이 EBS 경로는 인스턴스 EBS 대역에 묶인다고 설명한 부분과 방향이 같습니다. 다만 본편의 논점은 큰 인스턴스의 수 GB/s급 상한이고, 이 측정은 4 vCPU 노드와 기본 설정 gp3의 하한 쪽 사례입니다. 그래서 "gp3는 이만큼 느리다"는 근거로 쓸 수 없습니다. 볼륨 처리량 설정을 올리지 않은 조건에서 나온 값입니다.

| 쿼리 | Direct I/O 요청 | warm | 읽은 행 |
|---|---|---|---|
| Q1 키 범위 1시간 count | 13ms | 4ms | 16,385 |
| Q2 파드별 ERROR, 2일 창 | 0.57초 | 0.36초 | 2,800만 |
| Q3 `LIKE` 전 기간 풀스캔 | 31.5초 | 2.63초 | 1억 |
| Q4 네임스페이스별 p50·p99 | 1.34초 | 1.03초 | 1억 |
| Q5 trace_id 점 조회, 인덱스 없음 | 24.3초 | 1.13초 | 1억 |

## 5. 본편과 비교할 수 있는 것과 없는 것

| 구분 | 수치 | 본편과의 관계 |
|---|---|---|
| 스토리지와 무관 | 코덱별 압축률, 컬럼별 압축 비율 | 비교할 수 있음. 데이터 형태와 버전이 달라 절댓값은 참고용 |
| 스토리지와 무관 | `read_rows`, 인덱스 스킵 비율, 인덱스 크기 | 비교할 수 있음. 정렬 키·skip index의 원리는 매체와 상관없음 |
| 디스크에 묶임 | Direct I/O 요청의 풀스캔 시간(Q3, Q5) | 본편과 비교할 수 없음. gp3 100GiB 기본값에서 나온 하한 쪽 값 |
| CPU에 묶임 | 적재 속도, warm 쿼리 시간, ZSTD 스캔 지연 | 본편과 비교할 수 없음. 4 vCPU 노드(파드 한도 3.5 vCPU)의 값 |
| 방향만 일치 | 풀스캔이 볼륨·인스턴스 EBS 대역에 막힌다는 해석 | 본편의 EBS 대역 병목 설명과 같은 방향. 규모가 다름 |

본편과 어긋나는 결론은 없습니다. 다만 본편의 반론 문단은 신세대 CPU와 EBS 조합이 캐시된 쿼리에서 구세대 로컬 NVMe를 앞섰다는 Altinity의 사례를 소개하는데, 이 부록의 warm 수치도 같은 축입니다. 페이지 캐시에 오른 쿼리는 CPU에 묶이고, 캐시를 우회하면 볼륨 대역이 드러납니다. 한 조건에서 나온 두 값이 이렇게 갈리는 점이 이 측정의 쓸모입니다. 어느 조건이 운영 부하에 해당하는지는 원문도 본편도 답하지 않습니다.

## 6. 본편에 없던 보충

- 컬럼별 압축 내역. 본편에는 코덱이나 컬럼별 압축 수치가 없습니다. ID 문자열 하나가 전체 저장량의 약 40%를 차지한 사례가 보충이 됩니다.
- 정렬 키 범위 쿼리에서 읽은 행이 전체의 0.016%에 그친 사례와 `EXPLAIN indexes = 1`로 확인하는 방법.
- bloom filter skip index의 효과와 크기(1.5%). 본편은 인덱스 설계를 다루지 않습니다.
- 용량 계산의 함정. 원문은 EBS가 사용량이 아니라 프로비저닝한 용량으로 과금되므로 데이터가 8GiB여도 100GiB 볼륨 요금이 나온다고 짚었습니다.
- 원문이 스스로 밝힌 한계. 단일 노드, 합성 데이터, 복제·샤딩 없음, 원시 query_log 부재.

## 7. 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| 측정 일자 | 문서 갱신일(2026-09-11)만 있고 실제 측정일은 없음 |
| 적재의 반복 횟수와 편차 | 적재는 단일 결과이며 반복 여부는 언급 없음 |
| gp3 125MiB/s와 인스턴스 EBS 대역 중 병목 | 원문도 분리하지 못함 |
| 원시 query_log, 캐시 상태 | 문서에 포함되지 않음 |
| 처리량·IOPS를 올린 gp3, 로컬 NVMe 인스턴스에서의 같은 측정 | 원문에 없음 |
| 현행 LTS에서의 같은 수치 | 새 실행 예제만 있고 결과는 없음 |
